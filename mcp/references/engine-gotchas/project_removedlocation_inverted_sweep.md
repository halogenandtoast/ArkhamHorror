---
title: project_removedlocation_inverted_sweep
description: "RemovedLocation is not a central sweep — each entity self-discards for its own DIRECT placement; runGameMessage fans LAST so its pushes resolve FIRST"
---

Two separate traps, both hit by #5426 (Rod of Carnamagos' Scarlet Rot went to the discard pile instead of back to the bonded cards when the enemy it was attached to stood on a location that *A Tear in Reality* removed).

**1. `runGameMessage` pushes resolve in reverse source order.** `instance RunMessage Game` (`Game/Runner.hs`) runs `modeL.here/there` → `entitiesL` → … → `runGameMessage` **last**, and every push prepends. So (a) consecutive `push`/`pushAll` calls inside one `runGameMessage` branch resolve *backwards* — the first thing written resolves last — and (b) anything `runGameMessage` pushes resolves *before* every entity's own push for that same message. `runQueueT` does not apply: card/entity runners are wrapped in it (order preserved within one entity), `runGameMessage` is not. Anything that must resolve **after** entity reactions has to be queued by an earlier-fanning component (the mode) or as a sibling behind the triggering message.

**2. Location removal is inverted.** `RemovedLocation lid` in `Game/Runner.hs` is a **no-op**. Each of the Enemy / Event / Asset / Treachery / Investigator runners has its own `RemovedLocation lid` case that fires only for a *direct* placement — `isDirectlyAtLocation` (`Arkham/Placement.hs`) = `AtLocation lid` or `AttachedToLocation lid`. Attachments (`AttachedToEnemy`, `AttachedToAsset`, …), threat-area/play-area entities, vehicle occupants and swarm cards are deliberately **excluded**: they ride on their host's removal instead (`Event/Runner.hs` `Discard _ _ target | eventAttachedTarget a == Just target` and `RemovedFromPlay source | not (isSource a source)`; `Enemy/Runner.hs` `InvestigatorEliminated`; `RemoveEnemy` for `SwarmOf`).

**3. A removed entity keeps answering messages, with a stale placement.** `RemoveEvent` (and its Asset/Skill/Treachery siblings) does not delete the entity, it moves it into `actionRemovedEntities` -- which `instance RunMessage Game` still fans every message to. Worse, the copy it parks there comes from `getEvent`, a `HasGame` read, and `readGame` (`Arkham/Game.hs`) returns the IORef contents, i.e. the game as of the **start of the current message**. So anything a runner writes to its own attrs during the very message that removes it is thrown away. Setting `placementL .~ OutOfPlay RemovedZone` in the runner (the way `Asset/Runner.hs` does) therefore does *not* stop the parked copy from still looking `AttachedToEnemy`.

The consequence for #5426: after the Rot returned to the bonded pile via `PlaceInBonded`, its parked copy still matched `RemovedFromPlay source | not (isSource a source)` when the host enemy left play a few messages later, and discarded itself -- so the card ended up in `bondedCards` **and** the discard pile.

**How to apply:** guard any "react to my host leaving play" handler with a liveness *query*, not a placement check: `selectAny $ EventWithId a.id`. `getEventsMatching` (`Arkham/Game.hs`) reads only `entitiesL.eventsL` for non-`OutOfPlayEvent` matchers, so it is false for a parked copy and true for a live one. `getEventMaybe` is **not** a liveness test -- it finds removed entities too (which is how `Discarded (EventTarget ...)` still reached `AddToDiscard`). The same trap applies to assets, skills and treacheries; only the event side is fixed.

**Why:** the old central sweep selected with `enemyAt`/`eventAt`/`assetAt`, which resolve a location *transitively* through `placementLocation` (`Helpers/Location.hs`) — so an attachment counted as being "at" its host's location. Combined with trap 1 the branch discarded events **before** enemies, so the Rot was gone before its host ever reached `LeavePlay #when` and the forced `EnemyLeavesPlay` reaction never fired.

**How to apply:** do not re-add a central select-and-discard to `RemovedLocation`. Add a `RemovedLocation` case to the entity's own runner guarded by `isDirectlyAtLocation`, and push plain `toDiscard` — do **not** also `checkWindows` a `LeavePlay #when`. All four base runners already announce that window before removing themselves (`Enemy/Runner.hs` `Discard`; `Asset`/`Event`/`Treachery` `RemoveFromPlay`), and a second announce double-fires every `EnemyLeavesPlay #when (be a)` forced ability (Hunting Horror, Bianca die Katz, the Parasites, Alejandro's Plight, Impossible Pursuit, Recover the Relic).

The location entity itself is deleted by `Do (RemovedLocation lid)`, queued **behind** the announcement by `removedLocation` (`Message/Lifted/Location.hs`) at the two raise sites (`Scenario/Runner.hs` `RemoveLocation`, `HideousPalace.hs`). Push a bare `RemovedLocation` and the location entity never gets delisted.
